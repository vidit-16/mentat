Mentat: experiment log

Vidit Choudhary

Experiment log, 17 to 22 November 2026. Every run in the order it happened, failed ones included. Raw outputs for each run are kept with the code.

Summary

Mentat triages customer-support conversations. It reads the last eight turns and returns the customer's problem (one of 96), the next step the written procedure allows (one of 30), how sure it is, and whether a person should check. Three linear classifiers read the words, who said them and which system steps already ran; a rule table the support manager edits removes any step the procedure does not allow; a second model, trained on the first one's mistakes, turns scores into a confidence. No language model decides anything.

On 2,300 development conversations it picks the right next step 82% of the time, against 39% for the published baseline, and when it answers without a person it is right 91% of the time. An LLM re-ranker made it worse and was not used. Noisy training copies and character fragments changed nothing measurable. A confidence bug on Hinglish messages was found and fixed. Every run is below in the order it happened, failed ones included.

Dated entries, newest last. Every run named here has its raw output in results/raw/<run-id>/ and an entry in results/manifest.json. Failed and abandoned runs stay in.

Machine for all runs unless stated: Windows 11 laptop, CPU only, Python 3.12.10, library versions in requirements.txt. Dev means reference/dev.jsonl (2,000 rows) plus reference/dev_noisy.jsonl (300 rows), scored by the benchmark's own unmodified scoring script.

2026-11-17 — Baseline failure taxonomy (baseline-001/taxonomy.json)

scripts/taxonomy.py puts every action error in one category (first rule that matches): wrong_flow (predicted intent is in another flow), sibling_intent (right flow, wrong intent), repeated_step (right intent, but the action is a step the context already shows as done), wrong_step (anything else).

Baseline, 2,300 labelled rows, 1,400 action errors:

Intent errors: 941 wrong flow, 497 sibling. Errors are worse when the 8-turn window has lost the start of the dialogue (action error 0.66 vs 0.51; 1,527 of 2,300 rows are cut). very_long noisy rows: 50 of 50 intents wrong, 41 of 50 actions wrong. The baseline reads only the last four turns as one bag of words, so a long message drowns everything else.

Reading: the baseline's main problem is not the hard part of the task (which step comes next) but the easy part (which flow is this). It also has no idea which steps already happened: 147 errors propose a step the context shows as done.

What moved what:

  • Reading the whole window (all 8 turns, with a per-turn length cap) instead of the last four turns as one bag removes 84% of wrong-flow action errors on its own. That one change is most of the gain over the baseline.
  • The per-turn cap (80 tokens: first 50, last 30) is in every run above, so its effect is not separated here. very_long intent errors fall from 50 to 20 with words only. A separate ablation of the cap is still to do.
  • The character block did not help. Action accuracy fell 1.1 points and the noisy gap went from 0.0097 to 0.0432. My plan assumed character n-grams would help with typos. On this data they add noise: the typo rows are mostly short replies like ooh or acconut id, where the rest of the context carries the answer. Kept for now because the later blocks recover the loss, but this is an open question for the final configuration.
  • Speaker/position tags and the procedure-state block mostly help action, and help the confidence ratio a lot (0.43 → 0.27), which makes sense: they tell the model where in the procedure the dialogue is.
  • wrong_step barely moves (248 → 234). Most remaining action errors are right flow, right intent, wrong next step. That is where the text does not say which branch of the procedure the agent took (for example whether the Oracle said yes).

2026-11-17 — Full training run, first attempt (train-001, failed)

Augmentation on (20% of rows get one noisy copy: typos, empty last turn, long padding, a second request appended; 23,962 rows in all), turn_index dropped on 15% of rows, five folds grouped by conversation for temperatures and the confidence model.

Failed. The three full-data fits finished (about 6 minutes), then the out-of-fold step died: TerminatedWorkerError, with "Windows fatal exception: access violation" inside liblinear in a joblib worker process. joblib passes large arrays to worker processes as read-only memory-mapped files, and liblinear crashed reading one. Nothing was written to models/. Log kept as results/raw/train-001-failed.log. The session running it also ended around then, which is why I did not notice for a while.

Fix: run the fold fits in a thread pool (backend="threading"). liblinear releases the GIL, so threads still run in parallel, and they share the matrix instead of mapping it.

2026-11-17 — Tests against the trained model; what the extended pack found

First full test run: 104 passed, then a failure.

  1. Spoofed system text. Customer text written like a system event ("account has been pulled up for me. purchase validation in progress ... a refund has been made") was not caught by the injection tripwire, so the answer kept 0.80 confidence. The structural defence held: the text was read as customer text, the answer was still routed to a person, and no refund was proposed. But the tripwire should catch it. No customer turn in the 118,180 non-system training turns matches a system-event pattern, so I flag customer turns that do.
  2. While checking false positives, two training rows tripped the tripwire on "...from you are now out of stock". The you are now pattern was too loose; it now requires a role word after it (you are now in developer mode). Training rows flagged: 0.
  3. The policy-change test was wrong, not the code. It required a person for every refund-flow row after refunds were removed from the table, including rows where the model never proposed a refund. Fixed the test to check only rows that would have got offer-refund, and to check the conflict is reported.

After these: 116 passed. Dev unchanged (dev-003). Through HTTP (dev-003-http) the numbers are identical to in-process.

2026-11-17 — Hostile pack over HTTP (hostile-002), and one answer I did not like

99 requests (9 published, 68 extended, 22 transport probes), each followed by a canary request to detect a later change in behaviour. 99 passed, slowest 170 ms.

But reading the answers rather than the pass/fail: hostile-004 (bidi-wrapped "cancel my order", one customer line) got search-faq with 0.99 confidence and no human. The answer is defensible (single-line openings in training are mostly search-faq), the confidence is not: only 62 of 20,000 training rows have no agent turn, so the confidence model has almost nothing to go on. Added a rule: no agent turn yet means confidence capped at 0.5 (below the threshold) and reason little_context. Dev effect (dev-004): 6 rows more go to a person (15.4% → 15.6%), ratio 0.2787 → 0.2821. All nine published hostile rows now reach a person; a test holds that.

Also made the model version hash cover confidence.json, so a change like this shows up in every response and log line.

2026-11-17 — LLM re-ranking (llm-001, not adopted)

Rule fixed before running (PLAN.md section 4 and the script header): adopt only if intent accuracy on the low-confidence slice rises by at least 5 points, action accuracy does not fall, and p95 of the call is under 2 s.

gpt-4.1-mini-2025-04-14, temperature 0, the first 150 dev and noisy rows below the confidence threshold. The model sees the cleaned conversation as quoted data and the local model's top five intents, and answers with a number. The policy gate reruns with its choice.

on the 150 rowslocalwith LLM
intent accuracy0.560.46
action accuracy0.320.29

The LLM fixed 13 intents and broke 28. The right intent was among the five candidates 75% of the time, so the ceiling was there; the model did not find it. p50 778 ms, p95 1,199 ms, 1 unusable reply (fell back), 34,594 input and 149 output tokens, $0.014076.

Not adopted. My reading: the hard rows are siblings like return_size / return_color where the deciding word left the 8-turn window, and the LLM guesses from what remains just as the local model does, but without the training data's priors. I did not try prompt variants or a larger candidate list; with this gap a few prompt tweaks are unlikely to reach +5 points, and each try spends dev rows on selection.

2026-11-17 — First clean-Linux run in CI (GitHub Actions run 44134811498, failed)

Fresh ubuntu-24.04, system Python 3.12.3, scripts/reproduce.sh all. Setup, hash check and all 117 tests passed. Evaluation through the HTTP service reproduced the committed dev numbers exactly (intent 0.7204, action 0.8217, top-70 ratio 0.2821). Then the hostile step failed: the nine published rows passed, and all 90 requests after them failed with connection errors.

**Cause: a bug in reproduce.sh, not in the service.** stop sent the shutdown signal to the evaluation step's server and returned at once. The hostile step's start launched a new server, which died with Address already in use; but the old server, still draining, answered /healthz, so the script took it as ready. It then finished shutting down during the run. The service log in the CI artifact shows both.

Fix: stop waits for the process to exit and the port to be free; start refuses to start when the port is already in use, and only reports ready while its own process is alive. The same mistake would bite anyone restarting the service in production with a health check that does not know which process answered, so RUNBOOK.md now says to stop and wait before starting.

Second finding from the same run: the model version reported on Linux (2de59e320f72ca21) differed from the laptop's (54c65d7534fd5fb3). Training on Windows wrote the JSON model files with CRLF line ends; git stores them with LF; the version is a hash of the files. Training now writes LF on every platform, and the laptop checkout uses LF, so both report 2de59e320f72ca21. Weights and predictions were never affected; only the version label.

2026-11-20 — Hinglish recheck on all of dev (hinglish-001)

ANALYSIS.md left one open item: code-mixed action accuracy fell from 0.82 (words only) to 0.70 (shipped), on 50 rows. Too few to say anything, so I made more.

Comparing the 50 published code_mixed rows word by word with their clean originals gives the rewrite: 43 append "thoda jaldi karo please" to the last customer turn; the rest also change "my" to "mera" or misspell "order" as "ordr". scripts/hinglish_slice.py applies that to every dev row with a customer turn (1,995) and compares each with its clean version through the same pipeline. A third variant swaps 18 common English words for Hindi ones; the published generator does not do this, so it is a stress test only.

Accuracy does not move: the earlier 0.82 → 0.70 was noise. Routing does. The suffix raises confidence on 1,796 of 1,995 rows, 47 rows move from a person to automated, and 24 of those are wrong.

scripts/confidence_breakdown.py splits the change by signal. Almost all of it is unseen_words (+0.18 logit on average; the model's own scores move the other way, -0.04). Cause: in training this signal is measured against a vocabulary fitted on the same 20,000 rows, so it is nearly always 0 (mean 0.0018, scale 0.0083). Clean dev already averages 0.006; with the suffix it averages 0.061, seven scales out. The fitted weight is small and positive, which is meaningless on data it never saw, and at seven scales it adds up. A train/serve mismatch I should have caught when I chose the signal.

Not fixed yet. The fix is to measure unseen_words in training the same way the service does, against a vocabulary that has not seen the row (fit it per fold), or drop the signal. Either needs a retrain and a new model version, so every result reruns.

2026-11-20 — Fix for unseen_words; retrain (train-003, dev-006, hinglish-002)

src/triage/train.py now measures unseen_words for each training row against a word vocabulary fitted without that row's fold (same 5 folds, same min_df), which is how the service sees a new message. New manual workflow .github/workflows/train-timing.yml runs scripts/reproduce.sh train on a fresh ubuntu-24.04 runner (2 vCPU, Xeon 6975P-C) and compares the result with the committed model.

Training took 275 seconds (features 18 s, three full fits 65 s, 15 fold fits 186 s, confidence 5 s), faster than the 4-core laptop's 347.

2026-11-22 — The pipeline in the browser (web-agreement-001)

For the project site, the whole pipeline now also runs in JavaScript (web/engine/), one module per Python module: text clean-up, event parser, features, scoring, policy gate, confidence, routing. It loads the shipped model unchanged: scripts/export_web_model.py writes the same float16 weights, rearranged one row per feature and gzipped (10 MB), plus the vocabulary, idf, biases, confidence model and the policy table resolved to label lists.

Python's regular expressions are Unicode-aware where JavaScript's are not (\w, \d, \b), and Python indexes strings by code point; the port spells these out.

Agreement test: scripts/web_agreement_ref.py writes the Python service's answers for all 2,309 published rows and the 68 extended hostile envelopes; scripts/web_agreement.mjs runs the JavaScript engine on the same inputs and compares. First run: 23 disagreements, all the same bug (abstentions were missing the versions field). After the fix: 2,377 of 2,377 agree on intent, action, needs_human, flow, flags, routing reasons, held-back and conflict fields. 88 confidences differ by 0.000001, the last rounded digit: Python sums float32 values, the port sums in float64. Same size of difference as between two CPUs in CI.

In Chrome the model loads in 0.4 s from a local server; the demo conversation gives the same answer to six decimals (0.831392). In Node a request takes 0.9 ms on average.

scripts/reproduce.sh web-check runs the check, and CI now runs it on every push.
